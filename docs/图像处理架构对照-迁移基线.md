# 图像处理架构对照：dsh-vision-router 1.5.3 vs dsh-vision（text-llm-vision main）

> 用途：作为「场景级识图路由层」架构合并迁移的操刀基线
> 依据源码：`eval/dsh-vision-router-1.5.3/`（router，node 插件，index.js 7273 行 + lib/）
>            `origin/main`（dsh-vision，python MCP 引擎，vision_client.py 664 行 + prompts.py）
> 日期：2026-08-17

---

## 0. 一句话总览

| | dsh-vision-router 1.5.3 | dsh-vision（main 分支） |
|---|---|---|
| 定位 | **后端级识图服务链**：一张图沿「提供商降级链」递进识别，工具驱动 | **任务级场景路由引擎**：scan 判场景 → 路由表选引擎 → 分级识别 |
| 场景判定 | 软判定（视觉模型自报 `visual_kind`，7 类） | 硬判定（scan 显式分类，12 大类 + 子类 + 聚焦点） |
| 路由粒度 | 同一任务逐级试后端（本地→HTTP→内置兜底） | 不同任务类型走不同引擎/模型（scene.sub → engine） |
| 分级方式 | 面向后端健康（时间预算/熔断/重试） | 面向任务深度（档位 fast/standard/deep） |
| 集成形态 | dsh 插件（cordis 钩子 + 14 个 vision_* 工具，进程内） | MCP 外部进程 + 控制面板 + VSCode 扩展 |

**核心差异一句话**：router 解决「**这张图由哪个后端看**」，dsh-vision 解决「**这张图该用什么方式看**」。你重启项目要做的场景级路由层，正是把后者的判定能力以前置层形态嫁接到前者之上。

### 0.1 职责与概念归属（重要）

| 概念 | 提出者 | 落地实现 | 说明 |
|---|---|---|---|
| 场景级识图路由（按场景选引擎/方式） | **shaoqiuyuavailable（本仓库作者）**，基于其 dsh-vision 插件（scan 判场景 → 路由表选引擎） | **ysr666（dsh-vision-router 维护者）** 在 1.5.x 落地为「结构化预识别 1+x」视觉层 | 概念出自 dsh-vision，实现形态不同（软分类 vs 硬分类），两个独立代码库 |
| 后端降级链 / 免费兜底 / 预算熔断 | ysr666（router 既有能力） | ysr666 | 非本仓库概念 |
| freeCloudFirst（云端免费优先） | shaoqiuyuavailable（本次改动） | 本文档配套改动（见 §1.7） | 纯顺序增量，默认关 |
| **成本/速度的妥协与优化**（在群主已有实现与框架之上） | shaoqiuyuavailable 的持续职责 | 分阶段落地（本仓库前置层 + 可向 router 提交的增量） | 见 §4.4 |

> 术语纪律：**「分级识别」（档位 fast/standard/deep）只在 dsh-vision 存在**；dsh-vision-router 的文档与代码中没有该概念（只有面向后端健康的 时间预算/熔断/重试，以及 progressiveTools 渐进工具）。本文档一律不把 router 描述为"分级识别"。

## 1. dsh-vision-router 1.5.3 图像处理管线

### 1.1 管线总图

```
上传图片/截图
   │
   ▼
agent/pre-step 钩子（图片轮入口，index.js:4644）
   ├─ ① 附件登记   recordUploadedAttachments / scanSessionEventLog（增量扫会话事件日志）
   ├─ ② 工具产物清洗 sanitizeToolResultImages —— 工具结果里的图片块永不进模型请求
   ├─ ③ turn 状态  turnState / structuredBootstrapTurnState（1+x 门）
   ├─ ④ 即时本地翻译 instantDescribe（可选）：buildInstantLocalMap → imageMemory
   ├─ ⑤ 自动挂载   像素工具（autoActivateOnImage）+ 注入挂载提醒
   └─ ⑥ 图片块改写  rewriteHistoryImages（缓存命中→描述文本；未命中→附件标记）
                     （有 stealth/wrapper 适配器时原样保留，由适配器在模型输入层隐身改写）
   │
   ▼
agent/request 钩子（routingEnabled 时，index.js:4885）
   ├─ 图片轮 → 切到 chainRoute（vision-chain 适配器）或首个视觉模型
   └─ 纯文本轮 → reverseRouting 切回 textProvider（DeepSeek）
   │
   ▼
视觉工具（vision_describe 等，index.js:4936+）
   ├─ 预处理：sniffMediaType（魔数嗅探）/ downscaleImage（≤400 万像素）
   ├─ 缓存：cacheKeyFor + createCache（200 条 / 3600s）
   ├─ 降级链：resolveToolVisionPairs → pairs() 逐对尝试 → http 兜底
   └─ 总预算 + 熔断 + 轮级失败记忆（lib/vision-resilience.js）
```

### 1.2 预处理层

| 环节 | 实现 | 说明 |
|---|---|---|
| 格式嗅探 | `sniffMediaType(bytes)`（index.js:413） | 按魔数判断 png/jpeg/webp/gif，不信任扩展名（附件无扩展名） |
| 附件登记 | `recordUploadedAttachments` + `scanSessionEventLog` | 图片轮开始前登记，后续 vision_describe 可经 attachmentId 查回 |
| 工具产物清洗 | `sanitizeToolResultImages` + 会话面 shadow-sanitize | 两层防线：工具产生的图片块永不进模型请求；历史会话面也清洗 |
| 图片块改写 | `rewriteHistoryImages(messages, imageMemory)`（index.js:959） | 有缓存描述→替换为文本；无→替换为附件标记（模型可经 vision_describe 查） |
| 尺寸下采样 | `downscaleImage(bytes, maxPixels)`（index.js:1739） | vision_describe 上传路径重存缩小版；retina 截图 10MP+ 是延迟大头 |
| 缓存 | `createCache(maxEntries=200, ttl=3600s)` + `cacheKeyFor` | key = 可用对 + http 兜底 + contentIds + wantJson + question；同图同问直接命中 |

### 1.3 场景判定层：结构化预识别 1+x（structuredVisionBootstrap，默认关）

- **开关**：`structuredVisionBootstrap: false`（默认关；开启 = 每图片轮至少 2 次视觉调用）
- **第一遍（bootstrap，独占）**：`vision_bootstrap` 工具执行**任务无关**的整体观察，返回固定 schema：
  - `visual_kind`：chat | document | ui | code | general | mixed | unknown（7 类软分类）
  - 附带 `regions / visible_text / entities / relationships / uncertainties / recommended_followups`
- **强制 x≥1**：bootstrap 成功后模型**必须**再调 ≥1 个深挖工具（describe/ground/detect/ocr/colors/pixel_diff/long_screenshot_ocr）才能作答
- **turn 状态机**：`required → completed（bootstrap 返回）→ followupCompleted`；pre-step 按状态注入中文提醒（"不要预选 OCR/文档/UI/代码模式"）
- **互斥**：`instantDescribe` 仅在**未开启** structuredBootstrap 时生效（index.js:2854）
- **特性**：场景判定完全交给视觉模型自推断，不做硬分类——这就是它的"路由"（软路由，无路由表）

**软路由成立结论（2026-08-17，本仓库作者评估）**：识别方式维度（OCR / describe / detect）**软路由 + 强化提示词足够，不再硬拦截**。依据：
- OCR 是逐字转写，对 1/l、0/O、空格、换行存在系统性混淆，**强制路由到 OCR 反而有害**；模型结合上下文的语义理解（describe）往往更准
- 配套 OCR 提示词强化已落地（PR #177 提交 `a8384ca`，3 处模型可见文案）：语义优先 + OCR 专精白名单（可执行代码/精确引用/合同表单/表格数字/验证码/无语义锚点的生僻字）+ OCR 输出视为待交叉验证的证据
- 因此 chat / document / ui / code **取消硬拦截**（此前"四类拦截"方案作废）；前置层只保留两个机制性职责：**mixed 细分**（§4.6，软路由无法覆盖的缺陷）与**后端成本调度**（§1.7 freeCloudFirst 已落地，阶段/场景降档见 §4.5）

### 1.4 即时本地翻译（instantDescribe，1.5.x 保留但退居二线）

- 触发：`rewriteEnabled && !routingEnabled && instantDescribe && 有本地后端`
- `buildInstantLocalMap(ctx, messages, localProviders, {style, memory, timeoutMs, downscaleMaxPixels})`（index.js:2266）
  - 对**无缓存描述**的图片块直接调本地识别（local-ollama → local-lmstudio）
  - 结果写入 `imageMemory`（无界 Map，id → 描述）
  - 输出风格 `localDescribeStyle`：plain / structured（含【初步判断】【细节】【空间结构】【输入图尺寸】）
- 失败语义：无后端 / 连接失败 / 超时 → **静默回退**原有标记，绝不阻塞图片轮

### 1.5 后端降级链（可用性管理；非"分级识别"）

**链序（固定）**：

```
local-ollama → local-lmstudio → httpProviders（用户配置，按序）→ vision-http（内置 OVH 免费兜底 5 模型）
   （最前，隐私/零费）         （次之）                  （中间）                        （最后，免 key）
```

**降级控制（lib/vision-resilience.js）**：

| 机制 | 语义 |
|---|---|
| 任务总预算 `createDeadline` | 一次视觉任务共享 wall-clock 预算（`visionTaskTimeoutMs` 默认 45s）；链式后端**不能**叠加等待（每后端只拿剩余预算） |
| 熔断器 `createVisionCircuitBreaker` | AUTH/REGION/TOS → 按凭据指纹熔断 10 分钟（换 key 立即解）；RATE_LIMIT/QUOTA → Retry-After 感知冷却（默认 60s）；INVALID_REQUEST/NO_ADAPTER → **仅本轮**熔断；TIMEOUT/SERVER/NETWORK → 不熔断 |
| 轮级失败记忆 `createVisionTurnMemory` | 一轮内全后端失败后，本轮后续视觉调用**直接短路**（不重复网络尝试） |
| fair-share 预算 `weightedFallbackBudget` | 仅对本地后端生效的按权重分预算（`isLocalBackendPair` 限定） |
| 失败分类 `classifyVisionFailure` | 输出结构化错误码（VISION_AUTH_FAILED / RATE_LIMITED / TIMEOUT / BACKEND_UNAVAILABLE / BACKEND_UNAVAILABLE_THIS_TURN…）+ "不要改问法重试"的语义提示 |
| 能力预判 `resolveVisionBackendCapability` | 结构性不可用（非生成式视觉模型等）在尝试前过滤 |

### 1.6 工具层（14 个 vision_* 工具）

describe / ground / detect / crop / pixel_diff / colors / ocr / long_screenshot_ocr / trace / extract_foreground / present / html_screenshot / materialize / screenshot（桌面截图，boot-time opt-in）

- 每个工具独立超时/预算（如 `ocrTimeoutMs` 30s，OCR 本地 tesseract ≤12s + 视觉模型回退只拿剩余）
- 自动挂载：图片轮注入挂载提醒（autoActivateOnImage）；structuredBootstrap 开启时必挂深工具
- 工具描述内嵌 FAILURE SEMANTICS：后端故障时**不要**改问法重试，直接基于已有信息回答

### 1.7 freeCloudFirst：云端免费优先（本次新增，默认关）

**优化意图**：在群主既有的「付费 httpProviders 在前、内置免费 OVH 补全在后」链序之上，提供一个成本开关——开启后云端后端**先尝试内置 OVH 免费 5 模型**（免注册、免 API Key），付费端点仅在免费模型全部失败后兜底，尽量把云端识别成本降到零。本地后端（Ollama / LM Studio）不受影响，仍在最前。

**实现（纯顺序增量，严格零回归）**：

- `Config.freeCloudFirst: z.boolean().default(false)`（index.js Config）
- `orderedHttpProviders(config, freeFirst)`（导出函数）：对 `httpProvidersOf` 输出做**纯重排**——免费集（内置表大→小稳定序）在前、付费集（保持原相对顺序）在后；`httpProvidersOf`/`providersOf`/`localProvidersOf` **本体不动**（zero-regression gate 锁死）
- 消费点仅 2 处：`httpProviders()` 闭包（所有工具工具的 http 兜底）+ `httpRouteProviders()`（整轮路由/模型选择/测试连接）——bootstrap 走 vision_describe 同链，**自动获得免费优先**
- 稳定排序保证缓存 key 可复现；freeFallback=false 时开关 no-op（没有免费层可提前）

**影响面**（已评估）：熔断/轮级记忆 key 与顺序无关（零影响）；预算 share 数值随顺序微变（总和不变）；开关切换会缓存击穿（无害）；卡片新增「成本」分组展示该开关。**唯一真实权衡**：OVH 免费配额约 10 次/分（5 模型 × 2 次/分/IP），低频场景=真零成本，高频场景=免费层做闸门、付费兜底承接。

**验证**：`tests/free-cloud-first.test.js`（4 例）+ gate 新断言（默认关字节一致、freeFallback=false no-op）；全量 373/379 通过（6 skipped 为环境相关）。

## 2. dsh-vision（text-llm-vision main 分支）管线

### 2.1 管线总图

```
图像路径/b64
   │
   ▼
scan(path) ──第 1 次──► (描述, 大类, 小类, 聚焦点)   ← 场景判定
   │
   ▼
_route_engine(scene, sub)  ── 路由表查引擎 ──►  scene.sub 精确 → scene 大类 → _default
   │
   ▼
引擎（_ENGINES 注册表：ocr / vlm / table…）→ 事实文本统一进【细节】段
   │
   ▼
zoom(path, scene, sub) ──第 2 次──► 事实提取（按大类选清单，小类注入上下文）
   │
   ▼
guess(path, context, scene, sub, scan_desc) ──第 3 次──► 推测（基于事实+场景）
   │
   ▼
spatial（deep 档）──► 空间结构 / grounding（元素名 + bbox + 图片尺寸）
```

### 2.2 预处理

- `_to_b64` / `_downscale_b64`（识别前下采样）
- **缓存只在 deep 档启用**（fast/standard 各 1-2 次调用收益趋近零；deep = scan+zoom+guess+spatial 3-4 次才值得）
- 缓存 key = `模型 + 温度 + b64 + prompt`（换模型/温度不命中旧缓存）
- 并发限制 2（防请求排队堵死/显存溢出，fast 档轻并发贴图）

### 2.3 场景判定（scan）

- `scan(path) → (描述, 大类, 小类, 聚焦点)`；温度 0.15（防发散）
- 大类 12 个：person / animal / plant / food / vehicle / machine / screenshot / object / meme / scene / unknown / generic
- 单一事实源 = `config scenes` 的键（配置可新增场景类）；prompts_version≥2 才叠加 scenes/prompts 基线
- 子类随大类（如 scene: landscape/cityscape/indoor/nature/sky/weather/unknown；document: chat/code/report…）

### 2.4 场景路由（_route_engine 路由表）

- 匹配规则：`scene.sub` 精确 → `scene` 大类 → `_default`
- 引擎注册表 `_ENGINES = { "ocr": RapidOCR, "vlm": qwen2.5vl zoom, "table": … }`
- 基线路由：`document.chat → ocr`、`document.code → ocr`、`_default → vlm`
- **v1.5 模型级**：路由值支持 `"引擎:模型"`（如 `vlm:llava`），模型注册表 `models`（type=cloud → 云端厂商；type=ollama/未注册 → 本地该模型）——场景与模型解耦，全部由用户配置
- 回退语义（沿用容错，不报错）：
  - 引擎未注册（路由表指向不存在名字）→ 回退 vlm
  - 引擎异常 / 输出为空（OCR 提取不足）→ 回退 vlm
  - vlm 自身异常 → `[识别失败（引擎异常），已回退]` 占位

### 2.5 分级识别（档位 + 引擎）

- 档位 `PRECISION: fast | standard | deep`（识别精度档位，控制调用次数与深度）：
  - fast：1-2 次调用（轻）
  - standard：scan + zoom
  - deep：scan + zoom + guess + spatial（3-4 次，才启用缓存）
- 引擎：
  - `_engine_ocr`：RapidOCR（已有，提取不足返回 "" → 调用方回退 vlm）
  - `_engine_vlm`：qwen2.5vl 走 zoom（按类提示词：person/food/vehicle 等各有 zoom_ 清单）
  - grounding / spatial：元素名 + bbox + 图片尺寸（温度 0.0）
- 云端路由：`_use_cloud / _cloud_key`（v1.5 模型级云端路由：models 表 type=cloud → 云端该厂商；model 非空优先于全局后端判断）
- 提示词反幻觉：`_ANTI_HALLUC` 贯穿（"文字清晰照抄 / 模糊[无法识别]"、"不要编造"）

### 2.6 外围

- MCP 服务器（`mcp_server.py`，stdin 强制 UTF-8——中文 prompt 乱码根因已修）
- 控制面板 / 控制 API（`control_api.py` + `proxy.py`：`vision_level()` 档位状态与 proxy 同源）
- 反向代理（`proxy.py` / `start_proxy.py` / `restart_proxy.py`）
- VSCode 扩展（`vscode-ext/`）+ 批处理（`batch_identify.py` / `collect_images.py` / `scan_one.py`）
- 本仓库 main 分支另有 `docs/superpowers/specs/2026-08-14-vision-router-v1-design.md`（v1 路由设计，已批准）与 `2026-08-15-vision-router-model-management-design.md`（模型管理）

## 3. 异同对照表

| 维度 | router 1.5.3 | dsh-vision（main） |
|---|---|---|
| 集成形态 | dsh 插件（cordis 钩子 + 工具，**进程内**） | **MCP 外部进程** + 控制面板 + VSCode 扩展 |
| 场景判定 | 软：bootstrap 视觉模型自报 `visual_kind`（7 类，任务无关） | 硬：scan 显式分类（12 大类 + 子类 + 聚焦点，配置驱动） |
| 路由键 | 无路由表；按**后端提供商**降级 | 路由表：`scene.sub → 引擎(:模型)`，精确→大类→_default |
| 深度/健康控制 | 时间预算 + 熔断 + 重试（面向后端健康；无档位概念） | 档位 fast/standard/deep（面向任务深度）+ 引擎分工 |
| 预处理 | 魔数嗅探 + downscale + 工具产物 sanitize + 历史改写 + 缓存 | b64 转换 + downscale + 仅 deep 档缓存 + 并发 2 |
| 上下文注入 | imageMemory 缓存描述替换图片块 / 适配器隐身改写 | 识别文本进【细节】段（scan/zoom/guess 分节） |
| 本地后端 | Ollama + **LM Studio**（OpenAI/Anthropic 兼容双格式） | Ollama（qwen2.5vl） |
| 云端兜底 | **内置 OVH 免费 5 模型**（免 key，限 2 次/分/模型/IP） | 用户配置云端厂商（qwen-vl-plus 等，v1.5 模型级路由） |
| OCR | 本地 tesseract 优先 + 视觉模型回退（结构化模式强制 engine=vision 优先） | RapidOCR 优先 |
| 引导/多步 | 1+x：bootstrap（整体）→ x≥1 深挖（强制） | scan → zoom → guess → spatial（deep 档 3-4 次） |
| 任务类型感知 | **无**（不区分文档/UI/表格专用引擎，全走同一 VLM 链 + 通用工具） | **有**（document→ocr、table→table 引擎、_default→vlm） |
| 隐私边界 | 桌面截图 boot-time opt-in；图片内容不改动用户文件 | 本地优先；云端需显式配置 |
| 失败语义 | 结构化错误码 + 本轮短路 + "勿改问法重试" | 占位文本 + 引擎回退链（不报错） |

**互补性（为什么两者可叠加）**：
- router 强在**后端健康管理**（预算/熔断/降级/兜底）与**像素级工具集**——但它对"图是什么"不敏感
- dsh-vision 强在**任务类型感知**（场景→引擎/模型路由）与**分级深度控制**——但它是外部进程，集成重、无预算/熔断
- 你的新定位（场景级识图路由层）正好把 dsh-vision 的"任务感知"前置，router 继续当"服务链"在后——**前置层判场景，router 管执行与兜底**

## 4. 迁移建议（场景级识图路由层）

### 4.1 新架构定位

```
用户图片轮
   │
   ▼
【前置路由层 · 你的项目】（开关默认关，关闭完全透明）
   ├─ 场景判定：复用 1+x bootstrap 的 visual_kind（软）或独立 scan（硬，需本地模型）
   ├─ 路由决策：scene/sub → 指定 引擎工具 或 指定 provider（读路由表，配置驱动）
   └─ 分级：档位 fast/standard/deep → 决定后续视觉调用次数/工具集
   │
   ▼
【router 1.5.3 服务链】（不变）
   └─ provider 降级链 + 预算/熔断 + 14 工具 + OVH 兜底
```

### 4.2 结合点（把 dsh-vision 的判定嫁接到 router 的钩子上）

| dsh-vision 概念 | router 等价/落点 |
|---|---|
| scan（场景判定） | `vision_bootstrap`（软 visual_kind）或独立前置本地 scan 工具（硬分类） |
| 路由表 `scene.sub → engine` | 前置层自己的配置表；引擎可映射为：document→`vision_ocr`/`vision_long_screenshot_ocr`、ui→`vision_detect`/`vision_ground`、table→`vision_describe(json)`、code→`vision_ocr`、general→`vision_describe` |
| 档位 fast/standard/deep | 映射到 1+x 的 x 次数 / 允许的工具集（fast=仅 describe，deep=detect+ground+ocr 全套） |
| 引擎注册表 _ENGINES | 你的 `python/vision_client.py` 路由表（保持瘦客户端：判定在 python，执行仍是 router 工具） |
| 云端路由 models 表 | 直接落到 router 的 `httpProviders` / `extraVisionModels`（不必自建） |
| OCR 引擎 | 交给 router（tesseract + 视觉回退），不在前置层重复 |

### 4.3 必须守住的边界

1. **与 1+x 互斥**：开启 structuredVisionBootstrap 时，前置层不得再叠加自己的 scan（防 2+x 叠成 3+x）；二选一，或前置层直接复用 bootstrap 结果做路由键
2. **关闭完全透明**：开关关 = 行为与纯 router 完全一致（工具集、文案、调用次数、缓存 key 均不变）
3. **不碰其他插件的工具**：前置层只做"建议/排序"，最终执行仍走 router 的工具与降级链
4. **失败静默**：场景判定失败（本地模型不可用）→ 直接跳过前置层，交给 router 默认行为
5. **挂载方式**：复用 `agent/pre-step`（判场景注入路由提示）或 `agent/request`（切 provider），在 router 自己之前注册（order 更小）

### 4.4 建议文件规划（你 README 已定的框架）

- `src/index.ts`（极薄）：开关 + cordis 钩子（pre-step 判定注入 / request 切路由）+ 与 router 的互斥探测
- `python/vision_client.py`（瘦身版）：场景判定（本地 qwen2.5vl）+ 路由表（scene.sub → 引擎工具/provider）+ 档位映射；输出 JSON 供 index.ts 消费
- 复用 router 的能力清单：降级链、预算熔断、OVH 兜底、工具集、imageMemory、缓存——**全部不重复实现**

### 4.5 职责二：在群主实现之上的成本/速度妥协优化

针对 ysr666 的已有实现与大致框架，做**成本与速度**两个方向的妥协优化（持续职责，分阶段落地）：

**成本方向（少花钱）**
1. **云端免费优先（freeCloudFirst，已落地）**：免费 OVH 前置、付费仅兜底；低频=零成本
2. **阶段分级调用**：bootstrap/scan 阶段固定走本地轻量模型（qwen2.5vl 甚至 3b 档），云端大模型只留给深挖/验证——router 无此能力，前置层补
3. **场景感知降档（后端维度）**：document/UI 类场景不需要大模型——降档到**本地/免费后端**（配合 freeCloudFirst），识别方式由提示词引导（语义优先），**不强制 OCR**（OCR 字符级缺陷使其不适合作为硬路由目标，见 §1.3 软路由成立结论）
4. **成本记账**：前置层记录每张图实际用了哪级后端；超配额/超预算自动降档（fast 档跳过 guess）

**速度方向（少等待）**
1. **链序压缩**：在免费优先基础上，把确定不可用的后端（熔断 open / 结构性不可用）在链头直接剔除，减少无谓尝试
2. **并发探活**：对本地后端做一次性 health probe 并缓存（避免每轮都等 ECONNREFUSED 超时）
3. **预算感知的提示词裁剪**：长图/大图在 deep 档才做完整结构化，fast/standard 减少调用轮次（映射 dsh-vision 档位）
4. **缓存命中优先**：复用 router 的 imageMemory/cache 键空间，前置层不重复建缓存

**边界（与群主框架的约定）**：一切优化**默认关 / 默认不变**，可独立开关；能进 router 的（如 freeCloudFirst）以最小增量提交，进不了的（场景判定、档位映射）留在前置层；不复制群主已实现的预算/熔断/兜底。

### 4.6 混合场景（mixed）路由策略——参考 dsh-vision 分支路由

> **策略来源（明确标注）**：本策略参考 **dsh-vision（text-llm-vision main 分支）的混合路由模式**——
> 提交 `17aff58`（混合场景识别：scan 第三行「画面类型」+ 引擎按内容类型自适应）、
> `d9e233b`（**移除画面类型字段（8B 判不了）+ 混合场景候选列表解析兜底，聚焦点缺失不再掉 generic**——当前最新形态），
> 实现于 `vision_client.py` 的 `_parse_scene` / `_parse_scene_list` / `_parse_candidates` / `_build_branches` / `_route_engine` / `_run_engine` / `analyze`。
> 概念（scan 判场景 → 路由表选引擎）由本仓库作者提出，dsh-vision 为其原始实现，前置层在此之上做 router 生态适配。
>
> **演进与分支说明（防误用过时版本）**：dsh-vision 的混合识别经历两代——① 17aff58 的「画面类型字段」方案（scan 第三行输出画面类型，8B 判不了，**已废弃**）；② d9e233b 起的「候选列表 + 聚焦点 + 双分支」方案（**当前 main 主线的最新形态，本文档以此为准**）。另注意 `feat/mcp-primary-path` 实验分支（MCP 主路径改造）**移除了聚焦点/双分支/引擎路由表**，混合图退化为取候选第一项——该分支与本策略不兼容，参考时以 main 为准。

**问题**：router 的 1+x 对 `visual_kind = mixed`（混合图：文档+UI、UI+代码、人+界面…）无任何特殊处理——bootstrap 只把 mixed 当软信息返回，执行路径完全交给模型自由发挥，成本与正确性都不可控。

**缺陷实证（router 1.5.3 对 mixed 无后续策略）**：
- `lib/structured-bootstrap.js:77`：recommended_followups 兜底仅 `visualKind` 匹配 `/ui/` → `vision_detect`，**否则一律 `vision_describe`**——mixed 落进"否则"分支，无 mixed 特判
- index.js 全文件：`'mixed'` 仅出现在 visual_kind 枚举描述，**零处理逻辑**；pre-step 提醒、turn 状态机均不读 visual_kind
- 后果三连：① bootstrap 只输出"混合"，**不输出"哪几种类型 + 各在哪些区域"**（路由键不存在）；② 后续 x 深挖模型自由选，可能漏判另一半、该 OCR 的用 describe 概括；③ 混合图深挖次数 1-N 不可控

**补法：1+x 升级为「1 + mixed 细分 + x′」**——bootstrap 负责"发现 mixed"（第一遍），前置层负责"细分 mixed"（第二遍），分支各自深挖（x′ = 每分支 1 次系统指定工具）：

```
bootstrap → visual_kind = mixed
   ▼ 前置层「mixed 细分」（二选一）
   ├─ 路 a：复用 bootstrap 的 regions/entities 推断各区域内容类型（零新增调用，有噪声）
   └─ 路 b：追加一次轻量细分判定（本地 qwen2.5vl："混合了哪几种内容类型？各在什么区域？"，不烧云）
   ▼ 分支路由（下述机制）：≤2 分支，各分支独立注入工具白名单
   ▼ 各分支深挖 = 系统指定的 x′，1+x 结构保持
```

成本：现状 = bootstrap(1) + 模型自由(1-N)（低确定性）；前置层路 a = ≤3 次、路 b = ≤4 次（高确定性，细分用本地模型）。

**参考的机制（同构移植，语义从"主体分类"改为"内容类型"）**：

| dsh-vision 机制 | 前置层 mixed 处理（适配） |
|---|---|
| scan 候选列表 `person\|vehicle` + 聚焦点（`_parse_scene`） | bootstrap `visual_kind=mixed` + `regions/entities`（结构化 JSON，比文本解析更稳） |
| 候选防呆：聚焦点[0]优先 → 位置配对小类 → **≤3 候选才真实骑墙** → **绝不掉 generic** | 从 entities/regions 推断主导类 + 次类；解析失败 → 放行（generic 兜底，不硬拦） |
| `_build_branches`：主类必含 + 聚焦点差异类，**`_MAX_BRANCHES=2` 封顶** | 分支 ≤2（成本封顶同款；普通图自动 1 分支） |
| 分支级 `_route_engine(scene.sub)`：scene.sub → scene → _default | 每分支按 kind → **分支引导（软）**：document→语义优先（确需逐字才 OCR）、ui→detect/ground、code→逐字转写（可执行性例外，仍受提示词约束）、其余放行（§1.3 软路由成立结论：不硬拦截） |
| `_run_engine` 回退：未注册/异常 → vlm；主分支失败必有占位 | 分支指定方式失败 → 放行模型自由选择（保留逃生通道） |
| 聚焦点仅对 `_PHOTO_SCENES` 有效（内容类丢弃） | document/ui/code 是单一路径，不产生多分支；分支只出现在 mixed |

**前置层落地流程（mixed 时）**：

```
bootstrap → visual_kind=mixed
   │
   ├─ 从 entities/regions 推断 主导类型 + 次类型（≤2 分支）
   │     ├─ 只推断出 1 个 → 单分支（等同该类型的普通引导）
   │     ├─ 推断出 2 个 → 双分支：各分支独立注入引导指令
   │     └─ 推断失败 → 放行（模型自由，现状行为）
   │
   ├─ 分支引导（软，§1.3 结论：不硬拦截）：document→语义优先（确需逐字才 OCR）/ ui→detect,ground / code→逐字转写（可执行性例外）/ 其余放行
   ├─ 逐字分支（document/code）不掺用户提问（同 dsh-vision 逐字引擎语义：转写纯净）
   └─ 分支失败回退 → 放行该分支由模型补选工具（渐进暴露，不硬删工具）
```

**与 dsh-vision 的关键差异（适配说明）**：
1. dsh-vision 分支维度 = 图中多个**实体主体**（例如人+飞机，各自走引擎）；前置层分支维度 = 图中多种**内容类型**（文档+UI，各自走识别方式）——**机制同构，分类本体不同**
2. dsh-vision 靠正则解析 8B 文本输出（候选列表防呆复杂）；前置层消费 bootstrap 结构化 JSON（regions/entities），解析更稳，但 mixed 时 entities 可能缺失/杂，仍需同款防呆（失败放行）
3. 成本模型一致：分支 ≤2、每分支一次调用，混合图 = 2 次视觉调用（对应 dsh-vision 的 2 分支封顶哲学）

**落地状态**：已在本会话完成**机制评估**（上述映射）；代码落地随前置层 `python/vision_client.py`（瘦身版）一并实现——`mixed` 分支构建函数直接移植 `_build_branches` 语义（去重 + ≤2 封顶），路由表采用 `scene.sub → 引擎工具` 结构（同 `_route_engine` 匹配序）。

### 4.6.1 迁移影响面（dsh-vision 混合策略 → 前置层）

**结论：影响面集中且可控——真正"搬"的只有 ~40 行核心逻辑，其余全是适配重写；全部落在前置层，router 源码零改动。**

| 组件（dsh-vision） | 迁移方式 | 规模 |
|---|---|---|
| `_build_branches` + `_MAX_BRANCHES=2` | **直接移植**（主+次、去重、≤2 封顶） | ~15 行 |
| `_route_engine` 匹配序 + `_parse_route_value` | **同构移植**：值域换成 router 工具名 | ~20 行 |
| `_run_engine` 回退语义 | **改语义**：失败 → 放行模型自由 | ~10 行 |
| `_parse_scene`/`_parse_candidates`（120 行正则防呆） | **重写**：输入从 scan 文本换成 bootstrap 结构化 JSON；防呆思想保留（entities 缺失/杂 → 放行，绝不硬拦） | ~60-80 行 |
| `SCENES` 12 大类场景表 | **裁剪重写**：只保留 mixed 细分相关类（document/ui/code/table）+ 通用兜底 | 配置 schema |

**成本面**：混合图 ≤2 次视觉调用（同款封顶）；普通图 1 分支零增量；判定失败放行零增量。**互斥面**：与 freeCloudFirst/降级链/熔断零影响；与 instantDescribe 沿用互斥；与 progressiveTools 渐进暴露一致。

**规模合计**：直接移植 ~40 行 + 重写解析 ~60-80 行 + 新增（场景表/工具映射/档位映射/注入指令/互斥探测）~150-200 行 + 测试 10-15 例；**router 源码 0 改动**。

### 4.6.2 两条迁移路线取舍（重要：§4.6/§4.6.1 的前提标注）

> §4.6/§4.6.1 的映射表默认走**路线 1（复用 bootstrap）**。若选择路线 2（复制粘贴独立 scan），仅"解析层重写"一项不再适用（可整段复制 dsh-vision 代码），其余评估（分支构建/路由匹配/回退/成本封顶/防呆）**完全通用**——前期评估不白费。

**路线 1：复用 bootstrap（遵循 1+x 契约）**
- 前置层 mixed 分支消费 `vision_bootstrap` 的 `visual_kind=mixed` + `regions/entities`
- 解析层重写为 JSON 推断（~60-80 行）；必须保持 1+x 结构（bootstrap 独占第一遍，x≥1 深挖）
- 优点：不新增第一遍调用；缺点：解析层重写 + 依赖 bootstrap 输出质量

**路线 2：复制粘贴独立 scan（关闭 router 的 structuredVisionBootstrap）**
- 前置层**不复用 bootstrap**：自己的本地 scan（qwen2.5vl）当第一遍，`_parse_scene` 文本正则**整段复制** dsh-vision，仅调整顺序/命名
- **不能与 router 的 1+x 同时开启**（scan 插 bootstrap 前抢第一遍、插后变 2+x）→ 前置层开启时强制关 router 的 structuredVisionBootstrap（互斥探测，二选一）
- 前置层自己的 scan→分支 结构本身含"一遍 + 深挖引导"，覆盖 1+x 的价值
- 优点：**解析层零重写**、更贴合 dsh-vision 哲学、本地优先；成本：fast=scan 1 次（**比 1+x 起步 2 次更省**）、standard=scan+分支≤2（等价）
- 缺点：不用 router 的 bootstrap（放弃其任务无关整体观察 + 结构化 baseline 的额外信息）

**结论（本仓库作者倾向）**：路线 2 更符合"复制粘贴调整顺序"的迁移直觉与 local-first/成本优化职责——零解析重写、fast 档更省、与 dsh-vision 哲学一致；代价仅是不启用 router 的 bootstrap 1+x（前置层 scan→分支 已覆盖其核心价值）。两条路线共享同一套分支/防呆/成本评估。

**路线 1.5（本仓库作者的当前首选）：bootstrap 保留 + 仅 mixed 特判** = 「1 + mixed 细分 + x′」
- 第一遍仍为 router 的 bootstrap（1+x 的"1"）；`visual_kind ≠ mixed`（chat/document/ui/code/general）时**前置层零介入**，router 现状 1+x 原样（fixed 集可另做"判定即路由"，见 §4.6 之前讨论，属可选增强）
- `visual_kind = mixed` 时才叠加前置层：细分（路 a 复用 regions/entities / 路 b 本地追加判定）→ 分支路由（≤2 分支各自注入工具白名单）→ 分支深挖（x′≥1，由系统引导但仍是模型执行）
- 契约：非 mixed 零增量；mixed 时 bootstrap(1) + 引导 + x′（≥1）——1+x 结构严格保持
- 优点：对 router 契约侵入最小、多数图（非 mixed）零成本增量、混合图获得确定性；缺点：解析层仍需重写为消费 bootstrap 输出（只服务 mixed 分支）
- 取舍：mixed 占比低的场景下最优（最小介入换最大确定性收益）；mixed 占比高或想彻底摆脱 bootstrap 软输出 → 路线 2
